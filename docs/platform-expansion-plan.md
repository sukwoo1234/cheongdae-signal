# 플랫폼 확장 계획

최종 수정: 2026-10-03

이 문서는 청주대학교 단일 행사 서비스로 시작한 청대 시그널을 여러 학교·지역·관심사
커뮤니티를 지원하는 하나의 플랫폼으로 확장하기 위한 목표와 순서를 정의한다.

## 최종 목표

> 학교에서 시작해 지역과 관심사로 확장되는, 신뢰 가능한 새로운 인연 연결 플랫폼을 만든다.

청대 시그널은 청주대학교 학생을 위한 소규모 연결 서비스에서 출발한다. 장기적으로는
하나의 계정으로 학교·지역·관심사 기반 커뮤니티에 참여할 수 있게 하되, 전국 사용자를
한꺼번에 섞지 않고 검증된 커뮤니티를 하나씩 추가한다.

학교마다 별도 사이트를 만들지 않는다. 하나의 플랫폼 안에서 커뮤니티별로 다음 항목을
독립적으로 관리한다.

- 참가 자격과 인증 방식
- 행사 기간과 보드 개방 조건
- 카드·선택·매칭 데이터
- 관리자와 차단 정책
- 개인정보 보관 및 폐기

## 용어

이 문서에서 말하는 `SSO`는 기업용 SAML SSO가 아니라 카카오·구글 등을 이용한
**소셜 로그인(OAuth)** 을 뜻한다. 구현과 화면 문구에서는 혼동을 피하기 위해
`소셜 로그인`이라고 부른다.

소셜 로그인과 학교 소속 인증은 서로 다른 절차다.

| 구분 | 목적 | 예시 |
|---|---|---|
| 계정 인증 | 같은 사용자가 다시 로그인할 수 있게 함 | 카카오, 구글 |
| 소속 인증 | 어느 커뮤니티에 들어갈 수 있는지 확인 | 학교 이메일, 학교 SSO, 제한형 초대코드 |

## 학교 이메일 인증 원칙

운영자는 다른 학교의 학생 명단, 포털 비밀번호 또는 개인 정보를 알 필요가 없다.
지원 학교를 추가할 때 확인할 것은 해당 학교가 학생에게 제공하는 공식 이메일 체계다.

### 자동 인증 흐름

1. 운영자가 지원 학교와 공식 이메일 도메인을 등록한다.
2. 사용자가 학교를 선택하고 해당 학교 이메일을 입력한다.
3. 서비스가 일회용 인증번호를 발송한다.
4. 사용자가 학교 메일함에서 인증번호를 확인해 입력한다.
5. 성공하면 학교, 인증 방법, 인증 시각, 만료 시각을 멤버십에 저장한다.
6. 이후에는 소셜 로그인만으로 계정에 접근하고, 만료 시에만 학교 이메일을 재인증한다.

운영자는 사용자의 메일함에 접근하지 않는다. 인증번호를 받은 사용자가 해당 이메일을
실제로 통제한다는 사실만 시스템이 확인한다.

### 인증 표현의 한계

학교 이메일 인증은 엄밀히 말해 **현재 재학 여부가 아니라 학교 이메일 소유 여부**를
확인한다. 학교에 따라 졸업생·휴학생·교직원이 동일한 도메인을 사용할 수 있기 때문이다.

따라서 별도 학교 제휴나 포털 연동이 없는 동안에는 사용자 화면에 다음과 같이 표시한다.

> OO대학교 이메일 인증

`OO대학교 재학생 인증` 또는 `학교 공식 인증`이라는 표현은 사용하지 않는다. 서비스에는
다음 취지의 안내를 포함한다.

> 학교 이메일 소유 여부를 확인하는 절차이며, 해당 학교가 재학 여부를 공식 인증하거나
> 서비스와 제휴했다는 의미는 아닙니다.

### 학교 추가 체크리스트

- 학교 공식 홈페이지에서 학생 이메일 제공 여부를 확인한다.
- 학생 이메일의 공식 도메인과 주소 형식을 확인한다.
- 학생 전용인지, 졸업생·교직원과 공유하는지 확인한다.
- 해당 학교 재학생 또는 학교 구성원 한 명과 실제 메일 수신을 시험한다.
- 확인 근거와 시험 일자를 `institutions` 관리 정보에 기록한다.
- 확인이 불충분한 학교는 `지원 준비 중`으로 두고 가입을 열지 않는다.
- 멤버십은 6개월 또는 학기 단위로 재인증하도록 한다.

초대코드는 학교 인증을 대체하지 않는다. 시범 운영 인원 제한, 동아리·소모임 참여 또는
학교 이메일 체계가 없는 커뮤니티의 접근 통제에만 사용한다. 초대코드로 참여한 사용자는
학교 이메일 인증 사용자와 구분한다.

## 목표 데이터 구조

- `profiles`: 소셜 로그인 계정과 연결되는 사용자 프로필
- `institutions`: 학교 이름, 공식 도메인, 지원 상태, 인증 정책
- `communities`: 학교·지역·관심사 기반 커뮤니티
- `memberships`: 사용자, 커뮤니티, 인증 방법, 인증·만료 시각
- `events`: 커뮤니티별 행사 기간과 보드 설정
- `community_admins`: 커뮤니티별 운영 권한
- `invite_codes`: 만료·사용 횟수가 제한된 초대코드
- `community_bans`: 커뮤니티별 이용 제한

카드·선택·매칭 데이터에는 모두 커뮤니티와 행사 식별자를 포함한다. RLS와 민감정보 공개
RPC도 커뮤니티·행사 범위를 강제해야 한다.

## 구현 우선순위

### 0. 다음 회차 업데이트

현재 운영 행사를 종료하고 기존 방식으로 데이터를 폐기한 뒤 다음 기능을 함께 적용한다.

- `0024`: 학교 인증 계정과 성별을 동의하에 최대 6개월 유지
- `0025`: 인스타그램·카카오톡·휴대전화 연락 방법 탭형 선택
- 최신 운영 `main`과 기능 브랜치 통합
- 전체 테스트, 빌드 및 스테이징 회귀 테스트

이 단계에는 소셜 로그인을 포함하지 않는다. 이미 준비된 기능만 배포해 운영 위험을
제한한다.

### 1. 청대 운영 안정화

- 업데이트 이후 2~3회 운영한다.
- 재참여율, 카드 등록 전환율, 선택률, 실제 연락 여부와 신고 건수를 확인한다.
- 계정 유지·행사 데이터 폐기·연락 방법 표시가 반복 회차에서도 정상인지 검증한다.

### 2. 계정과 소속 인증 분리

소셜 로그인 버튼을 먼저 붙이지 않는다. 다음 구조를 먼저 설계하고 마이그레이션한다.

- 로그인 계정과 학교 이메일을 별도 개체로 분리한다.
- 한 사용자가 여러 인증 수단을 연결해도 계정이 중복 생성되지 않게 한다.
- 차단 기준을 로그인 이메일이 아니라 내부 사용자 ID와 검증된 식별자로 전환한다.
- 현재 이메일 기반 행사 가명 키 생성 방식을 새 계정 구조에 맞게 변경한다.
- 학교 인증의 발급·만료·취소 이력을 멤버십으로 관리한다.

### 3. 소셜 로그인 도입

- 카카오 또는 구글 중 한 제공자로 먼저 시작한다.
- 소셜 로그인 후 학교 이메일 최초 1회 인증을 연결한다.
- 기존 청대 계정과 신규 소셜 계정의 안전한 연결 절차를 제공한다.
- 로그인 제공자가 달라도 동일 사용자의 행사 선택 기회가 중복되지 않게 한다.

소셜 로그인은 다음 회차 기능 배포가 끝난 뒤 진행할 **확장판의 첫 번째 큰 개발 과제**다.
다만 실제 구현 순서는 `계정·멤버십 구조 설계 → 소셜 로그인 → 학교 인증 연결`이다.

### 4. 두 번째 학교 시범 운영

- 공식 학생 이메일 체계가 확인된 인근 학교 한 곳만 추가한다.
- 해당 학교 구성원과 메일 수신 및 인증 흐름을 시험한다.
- 학교별 카드·관리자·차단·데이터 폐기가 완전히 분리되는지 확인한다.
- `우리 학교 추가 요청`을 받아 다음 지원 학교의 우선순위를 정한다.

### 5. 지역·관심사 확장

- 기본 노출 범위는 본인 학교로 유지한다.
- 사용자가 원할 때만 인근 학교 또는 같은 지역 보드를 추가로 본다.
- 개인 GPS 대신 학교·캠퍼스·지역 단위의 거리만 사용한다.
- 생년월일 전체보다 연령대를 사용하고, 필요한 정보만 수집한다.
- 충분한 신고·차단·관리 체계를 마련한 뒤 학교 밖 커뮤니티를 연다.

## 배포 원칙

- 행사 진행 중에는 인증·계정·폐기 구조를 변경하지 않는다.
- DB 마이그레이션이 필요한 기능은 행사 종료와 데이터 폐기 후 적용한다.
- 확장 기능은 운영 `main`과 분리된 브랜치와 스테이징 환경에서 검증한다.
- 새로운 학교는 이메일 체계가 확인되기 전까지 가입을 허용하지 않는다.
- 학교 공식 서비스 또는 공식 재학 인증으로 오해할 수 있는 표현을 사용하지 않는다.
